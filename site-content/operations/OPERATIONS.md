# 運用と復旧

- 公開サイトの日次点検：.github/workflows/blog-audit.yml。mainで毎日21時UTC（日本時間翌6時）、手動起動も可能。
  GitHub Actionsが有効で利用枠内であることが前提。スケジュールは遅延・停止の可能性があり、常時監視ではない。
  現時点で実行済みなのはローカルからの公開HTTP点検。GitHubでの初回実行履歴は別途確認。
- 結果はActionsのartifactに30日保持。HTTPエラーは失敗、h1・description等は要確認の警告。
- 外部リンクはこの点検では自動アクセスしない。公式情報の料金・仕様等は記事更新時に確認。
- 月1回：Search Console（接続後）、古い日付や価格、孤立記事、重複検索意図、ASP終了案件、実体験の追記候補を確認。
- データ最小化：独自の概数集計は日付・記事slug・件数だけ。Cookie・IP・ユーザーIDは保存せず90日保持。
  同時更新とキャッシュの影響を受けるため正確なアクセス解析として扱わない。ASPのトラッキングは未導入。
- 本名は出さず「ひろがる趣味暮らし 管理人」。猫の年齢や未提供の実物写真・使用歴・試飲歴は作らない。

## バックアップの範囲

site-content/backups/before-polish-*.json は公開済みの専用記事・固定ページ・トップ設定の変更前コピー。
記事側にも最大10世代の変更前本文・表紙IDを保持。Gitには専用プラグインの各版を保持。
画像の旧メディアは削除しない。これらはサイト全体・DB・サーバーのバックアップではない。
ConoHaアカウントへの接続がないため、自動バックアップの有効性・復元日数・復元操作は未検証。

## 更新・障害

1. status / starter-review / site-auditを安全な編集接続で取得。キーを出力・コミットしない。
2. 変更前内容を退避し、テストを実行。ZIPと確定コミット・SHA256を用意。
3. plugin-updateはこの専用プラグインだけ。WordPress標準一時バックアップを利用。
4. 更新後に新しいリクエストでstatusと公開画面を確認。書込みエラーは直後に再送せず状態確認。
5. PHP不具合でサイトが開かない場合はWordPressリカバリーモードまたはConoHaのファイル管理が必要。
   管理画面で既知の正常版ZIPへ置き換える（APIは誤ったダウングレードを防ぐため版上昇のみ）。
6. 記事本文の復旧は履歴またはバックアップJSONを確認し、現在の指紋でmanaged-articleを実行。
   同時編集を無視して上書きしない。別プラグインの更新・削除はこの接続の対象外。

## Search Console（所有者の操作が必要）

https://search.google.com/search-console/welcome を本人のGoogleアカウントで開き、
URLプレフィックスに https://hirogarushumi.com/ を登録。「HTMLタグ」の確認用コードを取得する。
これはパスワードではない公開用の所有権確認トークン。受領後、専用site-verificationから設置可能。
Google画面で「確認」を押す操作と、サイトマップ wp-sitemap.xml の送信が必要。
タグの設置だけで所有権確認完了・検索データ接続完了とはしない。
今あるサイトマップ・公開設定を維持。noindexを解除しただけで検索掲載を保証しない。
